# План имплементации

Опирается на `requirements.md` и `decisions.md`. Сначала клиент, бэкенд в конце.

Клиент ходит в API через `fetch`.

Общее для обеих частей:

- клиент ходит только в `/api/tasks`;
- в базе нет поля позиции. Внутри колонки порядок — `createdAt` по убыванию;
- фильтр по приоритету живёт только в состоянии страницы;
- вход, несколько досок, поиск, сроки и ручная сортировка не делаются.

## 1. Каркас клиента

`client/` — Vite, React, TypeScript, MUI. Прокси `/api` на `http://localhost:3000` закладывается сразу, даже пока сервер не запущен.

Готово, когда клиент открывается и показывает три колонки.

Отдельного хранилища нет: список, загрузка, ошибка, фильтр и открытый диалог лежат в `Board`.

`tasksApi.ts` — функции `getTasks`, `createTask`, `updateTask`, `deleteTask`. Модуль ходит в `/api` через `fetch`. Ошибка сети и ответ не 2xx превращаются в исключение с текстом для экрана.

`constants.ts` хранит три колонки и подписи: `new` — «Новая», `in_progress` — «В работе», `done` — «Готово». Там же соседние переходы для кнопок:

| Откуда   | Кнопки                 |
| -------- | ---------------------- |
| Новая    | В работе               |
| В работе | В «Новая» и в «Готово» |
| Готово   | В работу               |

### Экран

При открытии страницы сразу запрос списка.

- Пока он идёт первый раз — индикатор загрузки, не пустая доска.
- Сбой загрузки — сообщение и кнопка «Повторить».
- Успех и ноль задач — пустая доска и кнопка «Создать задачу». Колонки при этом видны.
- В колонке без задач — короткая подпись «Нет задач».

Шире 900px колонки стоят в один ряд. Уже — друг под другом, без горизонтальной прокрутки страницы.

Карточка показывает название и приоритет. Цвета чипа: низкий — нейтральный, средний — предупреждение, высокий — ошибка. Подпись приоритета есть текстом, не только цветом.

Приоритет в форме — три радиокнопки: все варианты видны сразу.

### Диалоги

Один диалог задачи:

- создание: пустое название и описание, приоритет «средний»;
- просмотр и правка: открытие карточки заполняет поля текущими значениями, их можно изменить и сохранить.

Форма с подписями полей, `required` и пределами длины. Ошибки показываются после попытки сохранить, не во время набора. Кнопка сохранения блокируется только на время запроса. Диалог не закрывается, пока запрос не успешен. Введённый текст при ошибке остаётся.

Удаление — отдельное подтверждение. Запись удаляется только после успешного `DELETE`, корзины нет.

После успешного создания, правки, удаления или переноса кнопкой список заново читается через `GET`.

Перенос кнопкой вызывает `PATCH` со новым `status`. Кнопка блокируется, пока запрос идёт.

### Доступность

У страницы один `h1`, у колонок — `h2`. У кнопок переноса, удаления и повтора есть понятные подписи. Диалоги закрываются по Escape и содержат заголовок. Поля названия и описания связаны с подписями. Фильтр обёрнут в `search`.

Готово, когда руками проходит сценарий: создать, открыть, изменить, перенести кнопкой, обновить страницу, удалить. На узкой ширине тот же сценарий проходит кнопками.

## 3. Фронтенд: перетаскивание и фильтр

Библиотека — `@dnd-kit/core`. Колонка принимает карточку. Слушатель перетаскивания висит на всей карточке, отдельной ручки нет.

Смещение меньше 8px считается нажатием и открывает диалог. Большее смещение начинает перенос. Кнопки на карточке останавливают событие указателя и не начинают перетаскивание.

Ниже 900px сенсоры перетаскивания выключены. Остаются кнопки.

При отпускании над другой колонкой карточка сразу показывается в ней. Место внутри колонки считается по `createdAt`, а не по точке курсора. Затем уходит `PATCH` со `status`. Если запрос падает, карточка возвращается в прежнюю колонку и показывается ошибка. Отпускание над той же колонкой ничего не отправляет.

Фильтр над доской: «Все», «Низкий», «Средний», «Высокий». Он скрывает карточки в уже загруженном списке и сбрасывается при обновлении страницы. Если задачи есть, но ни одна не прошла фильтр, текст «Нет задач с таким приоритетом». Это состояние не заменяет пустую доску.

Готово, когда на широкой ширине карточку можно перенести за её площадь, ошибочный ответ возвращает её назад, а фильтр не меняет данные в базе.

### Схема

Модель `Task`: `id` UUID, `title`, `description`, `priority`, `status`, `createdAt`, `updatedAt`.

Prisma-перечисления:

- приоритет: `low`, `medium`, `high`, по умолчанию `medium`;
- статус: `new`, `in_progress`, `done`, по умолчанию `new`.

Одна миграция создаёт таблицу. Ручной SQL после запуска не используется.

### Поведение сервиса

`TasksService` — единственное место правил. Контроллер только принимает DTO и отдаёт результат.

| Действие    | Правило                                                                                            |
| ----------- | -------------------------------------------------------------------------------------------------- |
| Список      | `findMany`, сортировка `createdAt desc`                                                            |
| Создание    | Обрезать пробелы у названия и описания. Записать `status = new`. Приоритет из тела, иначе `medium` |
| Изменение   | Менять только переданные поля. Смена статуса не трогает название, описание и приоритет             |
| Удаление    | Если записи нет — 404. После удаления список её не содержит                                        |
| Пустая база | `[]`, не ошибка                                                                                    |
| Чужой `id`  | Не UUID — 400. UUID нет в базе — 404                                                               |

В `CreateTaskDto` нет поля `status`: колонку при создании выбирает сервер.

`UpdateTaskDto`: все поля необязательны. Пустое тело — 400. Неизвестный приоритет или статус — 400.

Пределы после обрезки пробелов: название 1–200 символов, описание 1–5000. Глобальный `ValidationPipe`: `whitelist`, `transform`, `forbidNonWhitelisted`.

Префикс приложения — `api`. Ответы об ошибках — стандартные ответы Nest: 400, 404, 500. Клиент читает `message`.

### Проверки

Сервис проверяется с подмененным Prisma, без живой базы:

1. создание без названия, без описания или с неизвестным приоритетом не доходит до записи;
2. создание сохраняет `status = new`;
3. смена статуса не затирает остальные поля;
4. в обновление попадают только переданные поля;
5. удаление отсутствующей задачи даёт 404;
6. пустой `findMany` возвращает `[]`.

HTTP-проверки через Supertest идут в PostgreSQL из Docker. Перед каждым тестом таблица очищается.

1. `POST` с пустым названием — 400, в базе ничего не появляется.
2. `POST` с корректным телом — 201 и `status: "new"`.
3. `PATCH` только со `status` оставляет название, описание и приоритет.
4. `PATCH` названия не меняет статус.
5. `DELETE` убирает задачу, следующий `GET` её не возвращает.
6. `GET` на пустой таблице — 200 и `[]`.
7. `GET` и `DELETE` неизвестного UUID — 404.

Готово, когда `pnpm test` проходит на поднятой базе, а клиент ходит в этот API.
